# 数据分析类技能的设计思路调研

调研目的：拆解公开数据分析技能如何把「业务理解 → 需要什么数据 → 源数据获取 → 清洗比对 → notebook 验证 → 分析 → 可视化」固化下来，提取可迁移的设计手法。

调研方式：安装并通读 6 个代表性技能的 `SKILL.md`、`references/`、`scripts/`，分析其流程设计、门禁机制与产物结构。

---

## 一、样本与覆盖

| 技能 | 覆盖环节 | 产物形态 | 代码量 |
| --- | --- | --- | --- |
| 指标体系设计助手（baige） | 业务理解 | 指标体系文档 + 硬校验 | 1 个校验脚本 |
| 数据指标体系搭建器·智遇 | 业务理解 | 九节报告 + 指标字典 CSV | 单文件 Web |
| 行业指标库 | 业务理解 → 需要什么数据 | 10 列指标表格 | 纯知识库，2483 条 |
| SQL 优化与数据建模 | 需要什么数据 → 取数 | 诊断报告 + DDL 清单 | 3 个脚本 |
| 数据分析协调器 | 预检 → 清洗 → 分析 → 交付 | DOCX + Markdown | 4 个脚本 |
| 数据分析与可视化交付 | 画像 → 选型 → 可视化 | 单文件 HTML | 13 图型 + 校验 |

**关键结论：没有一个技能覆盖笔记本（notebook）逐步验证环节。** 全部设计为「输入 → 一次性管线 → 成品」的批处理形态，见第四节。

## 二、逐环节的设计手法

### 1. 业务理解：结构化提问 + 硬门禁

三个指标体系类技能用了同一套路：**把开放的业务理解压成 4–5 个封闭问题，答不全就不许往下走**。

- 智遇：4 问（做什么产品 / 什么阶段 / 已在看什么 / 最头疼什么），**每次只问一个**，明确要求「不要一次甩清单」。产品不在预设 8 类里时，让用户用原话描述，工具自动归类，**并在报告顶部写明推断依据**。
- baige：5 项背景，`🔴 CHECKPOINT：业务描述、商业模式、阶段、本季度首要目标四项齐全，不满足则补问，不得直接定指标`。
- 数据分析协调器的核心原则第一条即：「先理解业务问题和指标口径，再计算；**不要从列名直接猜业务定义**」。

**可迁移点**：业务理解不是一个对话阶段，而是一张有必填项的表单 + 一道门禁。表单里最关键的字段是「本季度首要目标」——它决定了后面所有分析的方向。

### 2. 需要什么数据：从指标反推字段，而非从表反推需求

- 行业指标库的做法最彻底：每个指标固定 10 列输出，其中 **「计算公式 / 常用维度 / 数据来源」三列就是取数需求的全部内容**。指标定义完，取数字段清单自然就出来了。
- SQL 优化技能的 `intake-checklist` 给了「最小可用集四项 + 缺项时处理」的对照表：数据库版本缺失 → **停止分析**；表 DDL 缺失 → 结论降级为假设；执行计划缺失 → 先给索取命令清单，拿到再继续。

**可迁移点**：把「缺什么数据」和「缺了之后怎么办」写成一张表。缺信息的正确反应不是猜，是降级或索要。

### 3. 源数据获取：预检清单化

数据分析协调器的预检覆盖：文件存在性与扩展名、大小、Sheet 列表、编码、合并单元格、可读性。多 Sheet 时「先识别结构；**只有在多个 Sheet 都可能改变答案且无法合理推断时才询问用户**」——这是很克制的设计：能推断的不打扰人。

可视化技能的读表部分更贴近实战，列了多表工作簿的三个坑：

1. 表头行位置不定（常有一两行说明文字）→ **按关键词自动探测表头行，别硬编码行号**；
2. 表尾混入另一块小表 → 按主表关键列过滤噪声行；
3. 合并表头让列名与值错位 → 关键表回读原始单元格核对。

还有一个具体教训：`清洗必剥 \r\n 与 _x000d_，202607 列曾因此被误判全 0`。

### 4. 清洗比对：规则表 + 画像表

两种互补的手法：

**（a）清洗规则表**（数据提取指南）——七项穷举，每项带验证标准：

| 清洗项 | 处理方式 |
| --- | --- |
| 空行 | 删除完全空白行 |
| 合并单元格 | 拆分为多行，向下填充 |
| 数值 | 去千分位，纯数字字符串转数值 |
| 日期 | 统一 YYYY-MM-DD |
| 字符串 | 去首尾空格，保留中间空格 |
| 空值 | 空白 → null，仅空格 → `""` |
| 列名缺失 | `col_1`、`col_2` 占位 |

配套一条硬规则：**只做格式转换和清洗，不修改原始数据值**。

**（b）全列方差画像**（可视化技能）——每列打「唯一值数 + Top4 值」，据此判定列的性质：

| 唯一值数 | 判定 | 处理 |
| --- | --- | --- |
| = 1 | 零方差 | 宣布「无图可出」，不硬凑 |
| 2–6 | 分类型 | 可作类目 |
| 7–30 | 低基数 | 超过 8 个考虑合并 |
| > 30 | 连续型 | 走时间序列或分布 |

**这张表是清洗与可视化之间的桥梁**：它回答的不是「数据脏不脏」，而是「这一列能不能承载业务含义」。编号类唯一值列直接跳过。

### 5. notebook 逐步验证：空白

六个技能无一设计此环节。它们只有**交付前自检**，没有**过程中验证**：

- 数据分析协调器的第 9 步「验证」= 复算关键指标、分组汇总对总计、占比对 100%、图表与正文数字一致——这是交付前的对账。
- 可视化技能的自检清单 10 项 + `verify-charts.mjs` 跑 14 个 case——这是渲染的冒烟测试。
- baige 的 `metrics_check.py`——这是交付物的结构校验。

**没有技能设计「中间产物给人看、等人反馈、再往下走」的循环**。这是整条链路上唯一的结构性空白，也是 pandas + notebook 工作流相对技能的根本优势所在。

### 6. 数据分析：六类固定分析结构

数据分析协调器给了常用分析骨架：**总体趋势 → 结构贡献 → 同比/环比 → Top/Bottom → 异常点 → 可行动分群**。并要求「优先回答用户问题」，而不是按套路全跑一遍。

分析可靠性上有一条硬约束：「`summary` 仅可支持其实际包含的单列统计/频次，**不能替代跨列聚合**；大数据摘要模式无法回答分组问题时，先过滤/分块/预聚合或请用户拆分，不能用 20 行样本外推」。

### 7. 可视化：选型决策树 + 明确说不

- **决策树**按数据形状分流：连续时间序列 → 折线/面积；>40 期 → 发丝面积；离散类目 ≤12 且名短 → 柱状，否则横条；构成占比 → 百点场/刻度环；两连续变量 → 散点；多群体×两指标 → 哑铃；两离散交叉 → 热力；增减分解 → 瀑布。
- **每条选型都带红线**：折线单序列超 40 期看不清单点；雷达维度 >6 改用分组条形；热力少于 40 格色阶不明显改用表格；瀑布步序必须按业务因果排，不能按大小排；散点必须写「相关不等于因果」。
- **兜底机制**：形状不属于任何一类，或类目 >8 且颜色无稳定含义 → 退回表格，不硬凑。

「什么时候说不」是这套设计里最反直觉也最有价值的部分：数据支撑不了 3 个以上有信号维度 → 说「这份数据更适合附表，硬画图会误导」；零方差列占比过半 → 直接说哪几列无图可出。

## 三、六个可迁移的设计模式

### 模式 1：把「我不知道」变成一等公民（证据分级）

SQL 优化技能做得最硬：证据分三级 `实测`（有执行计划）/ `推算`（由 DDL 推断）/ `假设`（信息不足），**缺少统计信息的结论必须显式标注为假设，且报告中不得与实测结论混排**。

baige 的同款手法：基线/目标用户没给就写「待确认」，绝不编造；用户自述标「用户提供，未核实」。

数据分析协调器：**区分描述性发现、原因假设和行动建议；没有证据时不声称因果**。

> **这是所有高质量技能的共同底线。** 技能的可信度不来自它算得多准，而来自它清楚标注哪里不确定。

### 模式 2：反向指标 / 拒绝场景 —— 防自欺机制

baige 要求每条主攻方向配一个反向指标（优化获客配垃圾账号率、优化转化配退款率、优化活跃配低质内容占比），并且 `guards` 字段必填，校验脚本硬性要求 `counter_metrics` 非空——理由写得很直接：**没有反向指标的体系等于给作弊发许可证**。

可视化技能的对应物是「什么时候说不」的五种场景。

### 模式 3：口径四件套 —— 业务理解的可执行产物

「口径」在这几个技能里从来不是一个字符串，而是固定四件套：

```
分子 / 分母 + 统计周期 + 数据来源 + 负责人
```

智遇的指标字典六列：指标名 / 口径定义 / 计算方式 / 数据来源 / 频率 / 负责人。baige 的 `koujing` 字段在校验脚本里被逐个节点强制检查，缺一个就 exit 1。

### 模式 4：硬校验脚本 —— 规范从文档变成门禁

这是「技能」和「提示词模板」的分水岭。三个技能都配了脚本：

| 技能 | 脚本 | 校验什么 | 失败行为 |
| --- | --- | --- | --- |
| baige | `metrics_check.py` | 北极星唯一、每个指标口径非空、反向指标非空 | `exit 1`，**不输出半成品** |
| 可视化 | `verify-charts.mjs` | 14 个图型渲染 case | 交付前必跑 |
| SQL 优化 | `self_test.py` | 三个脚本冒烟 | 交付前必跑 |

`metrics_check.py` 的设计值得抄：它不只校验，还**顺便把通过的 JSON 渲染成指标树文本**，所以渲染结果天然可信。

### 模式 5：渐进式披露的文件结构

统一的四层结构：

```
SKILL.md          流程 + 红线（只放路由，绝不放全部细节）
references/       领域知识，按需加载
scripts/          确定性逻辑，不进模型
assets/           模板与样式正本
```

数据分析协调器在文末明写「**不要一次性加载全部 references**」，并给了一张「路径 / 内容 / 何时加载」的资源索引表。`data-extraction-guide.md` 开头甚至有反向导引：「**不要在阶段 3（分析）后读取**，避免重复执行解析逻辑」。

### 模式 6：先降级，不阻塞

图表失败 → 降级为数据表和文字，**不阻断报告**；文件超 100MB 或 10 万行 → 优先分块/预聚合，不机械抽样；少于 10 行或关键字段缺失率 >50% → 仍可描述，但**必须显著降低结论强度**。

降级是有代价的，所以每个降级动作都要求在报告里留痕。

## 四、结构性空白：没有技能设计 notebook 环节

六个技能的形态完全一致：**输入一次，管线跑完，输出成品**。中间没有可驻足、可讨论、可回退的状态。

这带来三个后果：

1. **口径错了要到成品阶段才发现**。数据分析协调器把「验证」放在第 9 步，即报告已生成之后。
2. **没有中间产物可供业务方确认**。业务方看到的是成品，只能接受或全盘否定。
3. **分析逻辑不可复用**。管线跑完只留下成品，下一次同类分析要从头再来。

而 notebook 工作流的本质恰好相反：**每一步都是一个可检查、可讨论、可回滚的状态**，并且代码与结论同屏，业务方能看到数是「怎么算出来的」。

这也解释了为什么这类技能的目标用户被明确定义为「非程序员」——可视化技能开头就写「目标用户是非程序员（运营、销售、做 PPT 的人）」。**它们填补的是没有代码能力的人的空白，不是替代有代码能力的人。**

## 五、对 scm-ana 的落点建议

现有结构（`sources / analysis / reporting` 分层 + `docs` 与代码目录一一对应 + raw/processed 双层归档）已经比这些技能更贴合业务。

更要紧的是：项目已有 `.workbuddy/skills/data-cleaning`，其「三层边界 + 六步流程 + 六类异常 + 五条判定原则 + 断言校验」的颗粒度**高于本调研中的任何一个技能**——六个技能的清洗段最多是一张七项规则表，而它是六类异常 × 处置决策 × 断言不变量。**清洗这一环不需要再补。**

对标之后，真正的空白只有三处：

### 1. 口径从「文档里的自然语言」变成「可校验的结构」

现状：`RULE_ROWS` 的 18 条口径写在 `reporting/excel.py` 里，`docs/降本分析/` 里有散落的定义。两者没有机器可读的一致性约束。

可借鉴 baige 的做法：把口径落成 `docs/降本分析/口径字典.json`，每条含 `名称 / 定义 / 计算公式 / 分子 / 分母 / 统计周期 / 数据来源 / 负责人`，再配一个 `scripts/check_koujing.py`——「优先谈判」这类档位缺口径就 exit 1。`RULE_ROWS` 从这个 JSON 生成，消灭两处维护。

### 2. notebook 加「契约头」（补齐六技能都缺的那一环）

六个技能都没有的环节，正是你项目的强项——`notebooks/采购入库数据清洗.ipynb` 已经承担了六步流程里的第 4、6 步。但它现在缺一个显式的开场声明。可以把第一格固化为契约：

```markdown
## 本 notebook 回答什么问题
## 口径（引用 口径字典.json 的哪个 key）
## 输入（read_inbound 的取数范围）
## 预期验证点（3-5 条，逐条打勾）
## 结论（稳定后提取到 src/ 的哪个模块）
```

好处是：业务方在 notebook 阶段就能确认口径，而不是等 Excel 报告出来才推翻重做。

### 3. reporting 层借可视化技能的「选型 + 说不」

`openpyxl` 只能出柱状/条形图，但选型决策和红线是可以直接搬的：

| 降本分析场景 | 该用的图型 | 红线 |
| --- | --- | --- |
| 降本额从基期到现期的增减分解 | 瀑布图 | 步序按业务因果排，不按大小排 |
| 同一物料谈判前 vs 谈判后单价 | 哑铃图 | 图例写清「哪个点是什么」 |
| 各采购员降本贡献排名 | 横向条形 | 首位用最深色 |
| 物料降本额 × 降本率分布 | 散点 | 图注必须写「相关不等于因果」 |

另有一条直接可用：**数据支撑不了 3 个以上有信号维度就退回表格**。降本核算里很多物料只有一两个月的对比数据，硬画趋势图会误导。
