# 第四步：指标验证与稳定脚本

> 产出：分析方案.md 的「四、指标验证与稳定脚本」+ 指标验证 notebook
> （模板：`templates/指标验证模版.ipynb`）；确认后把**指标计算**沉淀成稳定脚本
> （清洗脚本已在第三步落地），跑一遍同时落 `data/outputs/` 下的 **parquet + json** 两份结果。
> **输入是第三步已归档的 processed 数据**——本步不复述、不重放清洗逻辑。

## 怎么做

1. **从 processed 归档取数**：验证 notebook 直接读第三步归档的 processed 数据，
   不再从 raw 内存预演。对 processed 数据本身有异议 → 回第三步走清洗回路改脚本重归档，
   不在本步原地改数。
2. **一个指标一节、逐步展示**：验证 notebook 每节算一个指标，中间结果、分组明细
   都摆出来，每格以表格收尾——用户能自己核，不是只看结论。
   每节收尾那张表，就是这张输出表的**候选形态**（列 + 粒度）：业务在这格确认字段，
   不另开一轮抽象的表结构讨论。
3. **每个指标先声明粒度**：一行代表什么（一个物料×一个月？一张单？），加总是什么。
   粒度没说清，后面所有对账都是糊涂账。
4. **对账三件套**（对得上才算数）：
   - **对业务已知数**：1.3 盘出来的现有报表、口头数——对不上必须解释差异来源；
   - **对明细**：抽几笔手工按公式算，和结果对；
   - **对总账**：分层对——明细行数金额 → 分组小计 → 总计，逐层加总一致；
     有期初期末的（库存、余额类）首尾也要勾稽。
5. **对不上不许「解释过去」**：差异要么口径错、要么数据错、要么参照数本身错，
   查到根因才能继续；靠说法圆过去的不算对账。
6. **口径调整走回路**：算不出、或结果不符合业务认知 → 回 1.4 改原节，
   在 4.2 记「改了什么 / 为什么 / 谁同意」；不在 notebook 里悄悄绕。
7. **输出表用真实报表确认，不列抽象字段清单**（1.4 的指标落成哪几张表，就在 notebook 里定）：
   - 指标算完，把它的**结果报表**直接摆出来：一行代表什么（粒度）、有哪些列、单位是什么，
     配全量 dataframe 让业务逐笔翻——业务对着真表说话，比对着一堆字段名靠谱；
   - 业务在 notebook 里逐张过：要哪些列、粒度对不对、该拆还是该合——改了重跑这一节，
     直到这张表就是他要的那张；
   - 确认完一张记一张卡片：**表名 / 粒度（主键）/ 列（含单位与口径）/ 更新方式 / 归档路径
     `data/outputs/<场景>/<YYYY>/<YYYY-MM>/<业务结束日>/`**，落 4.3——没确认的表不进脚本；
   - 表清单 = notebook 里确认过的那几张报表，不在文档里另起一套字段名；
   - 每张表同时声明**看板读哪几块**（KPI 要哪几列、趋势要哪张月度表、下钻要哪层明细），
     这块没定，第五步就得回头改脚本。
8. **确认后沉淀指标脚本**：
   - 验证过的指标计算逐段搬进 src（分层去向：取数 sources / 指标 analysis / 导出
     reporting——清洗已在第三步进 clean 层）；
   - 窗口、阈值全收进 Config 参数，不写死；
   - 离线测试：合成小数据跑关键断言（指标边界、分层加总）；
   - 一条命令复跑：跑完产出 **outputs 归档**，路径写进 4.3。
9. **归档落两份，一次运行同时产出**（不要事后手工补第二份）：
   - 调用 `src/reporting/metrics.py` 的 `archive_metrics(frame, scene, snapshot_date, tables=..., meta=...)`：

     ```python
     from reporting.metrics import archive_metrics
     paths = archive_metrics(
         report,                                  # 主表：一行一业务粒度
         scene="采购增量分析",                     # 与 notebooks/<场景>/ 同名
         snapshot_date="2026-09-30",              # 业务结束日，不是跑数日
         tables={"月度数据": monthly, "优先级汇总": priority_summary},
         meta={"window_start": "2025-10-01", "window_end": "2026-09-30",
               "data_file": read_meta["data_file"],          # 取数 meta 里的数据文件
               "entrypoint": "uv run python scripts/run_analysis.py"},
     )
     ```

   - 落到同一个业务日期目录，两份同源：

     ```text
     data/outputs/采购增量分析/2026/2026-09/2026-09-30/data.parquet   # 复算与对拍
     data/outputs/采购增量分析/2026/2026-09/2026-09-30/data.json      # 看板取数的数据契约
     ```

   - `data.json` 结构固定三层，第五步只认这个结构、不再解析 parquet：
     `meta`（场景、业务日期、生成时间、窗口、来源文件、行数、脚本入口）+
     `tables`（`detail` 主表 + 声明的其它块，每块 `columns` 列名 + `rows` 逐行记录，
     NaN 落成 `null`）；
   - **口径留痕进 `meta`**：窗口、数据时点、来源文件、脚本入口——网页上要能自证来路；
   - parquet 与 json 的**行数、列名、金额合计逐项对得上**（同一份 frame，不该有差）。
10. **沉淀后对拍**：同窗口下指标脚本结果与验证 notebook 逐数一致
    （含 outputs 归档表与 notebook 结果一致），一致才算落地。

## 规则

- 输出见铁律 2（明细交 dataframe、输出格只放汇总表）。
- 测试用合成数据，不依赖真实归档。
- 输出物自带数据口径信息（窗口、数据时点、来源文件）——报告要能自证来路。
- parquet 与 json 同一次运行产出，只改一份等于两份口径打架，第五步会照着旧 json 画图。
- 稳定脚本的产出是第五步看板的直接输入，第五步不重算。
