# 第四步：指标验证与稳定脚本

> 产出：分析方案.md 的「四、指标验证与稳定脚本」+ 指标验证 notebook
> （模板：`templates/指标验证模版.ipynb`）+ 稳定指标脚本 + 同批 outputs 归档。
> 输入是第三步已归档的 processed，本步不重放清洗。读取、归档及模块职责以
> [数据与代码约定](数据与代码约定.md) 为准；下方接口示例需先核对或补齐实现。

## 怎么做

1. **显式读 processed**：用 `read_processed_<数据集>()`，正式复跑用对应 `*_meta()` 留痕。
   声明依赖的数据集、schema/规则版本和窗口；入口校验必需字段、类型、粒度与覆盖。
   缺字段、缺档、过期就明确失败；不能退回 raw、静默跳过或在本步补洗。
   来源标准有问题回第三步，场景业务过滤和衍生计算保留在分析层。
2. **一个指标一节**：每节写口径、粒度、公式、输入与中间量。完整中间明细保留为命名 dataframe，
   输出格展示全量汇总，不用 head/tail/sample 代替明细。
3. **先声明粒度**：一行代表什么、键是什么、金额单位和税口径、空值与零分别表示什么、能否跨维度加总。
   一对多 join、重分摊或加权指标单独说明，不能直接对百分比求和。
4. **对账三件套**：
   - 对业务已知数：引用 1.3 的参考报表与条件，差异定位到口径或数据。
   - 对明细：选定有定位条件的业务记录手工复算；完整明细仍保留。
   - 对总账：明细 → 分组 → 总计逐层核对；有期初期末的再做首尾勾稽。
   数值使用业务确认的精度/容差，先比原始值再格式化；空值不能用零掩盖。
5. **差异查到根因再继续**：数据错误回第二/三步；指标口径错误回 1.4，并在 4.2 记录修改、原因和确认。
   参考数有问题也要有可复核证据，不能只补一句解释。
6. **按真实报表逐张确认输出**：完整结果以命名 dataframe 供翻查，每张记
   表名 / 粒度与键 / 字段及单位口径 / 更新方式 / 看板用途 / parquet 路径，写入 4.3。
   主表统一键为 `detail`；其他表的名字与 JSON `tables` 键、文件清单一致。
   月度趋势、分组汇总若是确认结果表，也必须有 parquet，不能只塞进 JSON。
7. **确认后沉淀指标脚本**：
   - 分析函数显式接收 processed dataframe 与配置，多来源输入分别声明；返回命名结果表与元数据。
   - 可变窗口、阈值进参数，稳定业务常量命名表达；不复制来源清洗逻辑，不在函数内隐式取数或导出文件。
   - 入口脚本按场景命名，串联读取、分析、校验、归档；最终报表可消费同一批结果导出 Excel。
   - 合成数据验证指标边界、分层加总，以及真实清洗输出能进入分析的衔接；不只测彼此隔离的函数。
8. **同一次运行归档所有表并生成 JSON**：以下是目标接口示意，不是当前仓库已实现的命令。

   ```python
   from archive import write_outputs

   paths = write_outputs(
       tables={"detail": report, "monthly": monthly, "priority_summary": priority_summary},
       scene="采购增量分析",
       snapshot_date="2026-09-30",  # 业务结束日，计算时间另记
       meta={"window_start": "2025-10-01", "window_end": "2026-09-30",
             "inputs": read_meta, "parameters": parameters,
             "entrypoint": "uv run python scripts/run_procurement_increment.py"},
   )
   ```

   主表为 `data.parquet`，其他表为 `tables/<表名>.parquet`，同目录生成 `data.json` 和 `manifest.json`。
   `write_outputs()` 返回实际批次标识、各表 parquet 路径、JSON 与 manifest 路径；
   JSON `meta` 引用批次，`tables` 覆盖全部确认结果表。全部校验通过才发布可读批次，失败不暴露半批结果。
   存量 `reporting.metrics.archive_metrics()` 仅归档主表、附表只进 JSON，不能当成已满足此约定；
   缺少多表/批次能力时先补实现并验证，再运行正式归档。
9. **从指定批次读回对拍**：
   - 使用 `read_outputs(场景, 业务结束日, table=表名, batch_id=批次)`，逐张对比 notebook、脚本与 parquet。
   - 对比 JSON 的表集合、列名、行数、空值及全部指标值；日期序列化按声明格式还原，不靠金额总和相等替代明细一致。
   - 实际计算差异并断言，不能手填「一致=True」；报表中的舍入只用于展示。
   - 同时核对 manifest 的输入版本、参数与结果批次；不能默认读最新结果来核对历史窗口。
