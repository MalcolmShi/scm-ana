# 第二步：数据源与归档

> 产出：分析方案.md 的「二、数据源与归档」。拿第一步 1.5 的字段清单去找业务要数据，
> 这一步不改业务字段、取值或单位。工程细节见 [数据与代码约定](数据与代码约定.md)。

## 怎么做

1. **问业务要数据源**（2.1）：按 1.5 清单逐项报需要的字段，问「这些数从哪来」——
   系统导出、既有报表、人工台账都算。每个数据源记六样：名称、提供方、
   给到形式（Excel 导出 / 接口 / 表）、更新频率、覆盖期间、已知的坑。
   再多问一句：「这数据有什么已知的坑？」——提供方自己知道的异常、口径特例、
   历史变更，原话记进 2.1，这是第三步排查的先验线索。
   先查已有来源文档和 processed 数据集：满足字段、版本、粒度与覆盖的直接复用，
   场景引用来源文档，不重复接入或定义另一套清洗标准。
2. **源文件先体检再对字段**：能否打开、Sheet 结构、表头在第几行（按关键词探测，
   导出文件常带说明行，别硬编码行号）、表尾有没有混小表、行数与时间跨度、
   字符串里有没有 \r\n / _x000d_ 这类脏字符。结构没看清，对字段是白对。
3. **字段对照**（2.2）：1.5 清单 vs 源字段，逐项给结论——直接有 / 改名可对 / 要换算 / 缺。
   对照不只对「有没有」，还要对「是不是一个意思」：同名未必同义——
   单位（元 / 万元）、含税口径、精度、字段在两个系统里的含义差异，逐项确认。
   缺的字段逐条找业务谈：有什么别的数据、或换什么算法口径能替着把指标算出来。
   替代方案经业务确认才写入 2.2，写明「缺什么 → 用什么替 → 对指标口径的影响」。
   对照结果用**两张清单**给业务过会，勾选式确认：
   - **表 A · 本次所需字段**：`分析字段 ↔ 原字段` 成对列出，带用途和清洗动作
     （改名、类型转换、空值填充都算）——业务确认名字和口径；
   - **表 B · 可选原字段池**：源数据**其余字段全量**列出、逐个给一句说明，
     有潜在价值的标 🌟 推荐、写明适用场景——业务按需勾进表 A；
     没被勾的记「暂不纳入 + 一句话原因」留档，下次同源场景直接复用这份池子。
   **确认标准字段**：源字段 → processed 标准字段 → 场景用途成对记录。
   标准字段已有定义则沿用；新增定义在来源文档确认粒度、键、类型、单位、税口径、空值和日期含义，
   并检查已有消费场景。表 A 是本场景所需投影，不是共享 processed 的裁列清单。
   源字段名保留在 raw、映射与清洗研究中；分析读取标准字段，报表展示名可另作映射。
4. **定归档方案**（2.3）：先区分业务日增量明细还是全量快照。
   日明细按业务日写入 DuckDB `raw.<来源>`；
   全量快照另声明快照日期与业务日期、读取一版的规则，不能把多次全量快照拼接计数。
   记录覆盖、无业务日期的识别依据、更新频率、重复导入和更正留版规则、元数据字段及原始文件留存位置。
   取数时间与业务日期分别记录，已有 `_source`/`_fetched_at` 不强制改成 `updated_at`。
5. **入档执行与读回**：来源模块只实现接入特性，复用公共归档写入；
   用按来源命名的脚本运行，实际命令写进方案，不复制采购入库的日期扫描、线程与取数实现。
   用 `read_raw_<来源>()` 读回指定窗口/版本，核对行数、业务金额和覆盖；
   日期无效或源文件存在不明跳过行时列出全量明细与处置依据，不能静默丢弃。

## 规则

- **验收标准是 1.5 清单**，不是「表里有什么就用什么」。1.5 每个字段都有结论
  （有 / 换算 / 替代且业务确认），数据源才算过关。
- 源字段名照抄进 2.2，不转译；转译过的名字没法回头核对。
- raw 层永远原样，清洗是第三步的事。
- 来源共享约定写回 `notebooks/数据清洗/`，场景 2.1~2.3 记录依赖版本、字段投影及链接。
- 业务给不了的数据源，在 2.1 记「待提供」和卡点，不拿别的表凑数。

## 完成标志

2.1~2.3 三小节齐：字段缺口为零（或缺口已有业务确认的替代方案）、**分析侧标准字段名经业务确认**、
归档类型、数据表与节奏已定、指定版本的数据已入档且读回对拍通过。之后进第三步（数据清洗与聚合）。
未到数据只记「待提供」和时间，不宣称取数依赖已满足。
