# 第三步：数据清洗与聚合

> 产出：分析方案.md 的「三、数据清洗与聚合」+ 一个逐项确认的清洗 notebook
> + 清洗稳定脚本 + processed 归档。
> 输入用 `read_raw_<来源>()` 显式读取第二步归档的 raw。
> 清洗按来源共享标准明细展开；表 A 是本场景所需字段，不限制其他场景复用的底表。
> 一切清洗在内存里预演，raw 不动。业务确认清洗后完整 df 之后，
> 才沉淀脚本、落 processed 归档；第四步起一律从 processed 归档取数。

已有 processed 的标准、清洗规则、输入版本与覆盖均满足本场景时，引用来源确认记录与归档，
只核对新增需求，不重复清洗。共享标准、读写职责及版本见 [数据与代码约定](数据与代码约定.md)。

## 怎么做

1. **先画像，后逐类**：清洗 notebook 第一节给全列画像——类型、空值率、唯一值数、
   枚举频数、数值列分位。用它定位可疑列（空值率畸高、唯一值数=1 的零方差列、类型混杂），
   定排查优先级。画像只是地图，异常结论要逐类核实。

2. **按质量维度系统枚举异常，不想到哪查到哪**：

   | 维度 | 查什么 | 例子 |
   | --- | --- | --- |
   | 唯一性 | 完全重复行；业务键重复 | 同一单号+物料多行：真重复还是合法多次？问业务 |
   | 完整性 | 关键字段空值、整行空 | 维度键空→行无法归属；金额数量空→无法聚合 |
   | 有效性 | 类型格式、枚举域、编码、脏字符 | 日期不像日期、千分位/全角数字、域外枚举、\r\n 与 _x000d_ |
   | 一致性 | 行内勾稽、跨表矛盾 | 单价×数量≈金额？单位全表唯一？两边同一事实对不上 |
   | 准确性 | 业务规则违背、离群值 | 负数、成本倒挂、未来日期、金额极端值 |
   | 及时性 | 覆盖断档、更新滞后 | 缺月缺日、快照落后业务期 |

3. **排查有顺序**：结构格式 → 重复 → 空值 → 勾稽 → 离群。
   前面的问题会污染后面：重复行会放大离群，格式未统一会影响空值统计。
   排查顺序不是自动处置顺序；重复的业务含义未确认前不能先删。

4. **notebook 一次生成，逐项确认**：全部排查节**一口气生成并执行完**（省去每节
   等一轮的来回），但**确认仍然一项一项过**——按节逐项给业务看、有异议改了重跑
   对应节；确认一类过一类，绝不因为一次生成就把确认也囫囵吞掉。
   notebook 骨架见 `templates/数据清洗模版.ipynb`，复制改名即用，措辞面向业务方。
   **每节汇报统一三段式**，业务只看这三块就够：
   - **总结**：一两句话——影响多少行/多少钱、要不要紧、结论倾向；
   - **明细**：问题全量明细以命名 dataframe 交付，输出格只放汇总表（见铁律 2）；
   - **建议**：修格式 / 剔除（记行数金额）/ 保留并标注，一句话理由 + 待拍板项。

5. **处置只有三种，逐一留痕**：格式修复 / 剔除（记行数与金额）/ 保留并标注。
   离群值特殊：统计方法（分位、IQR）只负责**产生候选**，处置必须由业务规则裁决；
   拿不准的标「待确认」，不自行删改。

6. **落笔 3.1 / 3.2**：每类异常记「维度 / 现象 / 行数 / 处置 / 业务结论」；
   清洗逻辑成文（动哪个字段、怎么动、为什么）。

7. **清洗后完整 df 确认 → 落 processed 归档**（第三步的收口，缺一不可）：
   - notebook 末尾把确认过的处理全部套上，将**清洗后完整 df 保留为命名变量**，
     交给用户翻查（Data Wrangler / 变量查看器），输出格只放摘要，**不导 Excel、
     不渲染整张明细**；并**主动提醒业务逐列过目确认**——这是进 processed 前
     的最后一道关，确认了才往下走；
   - 确认后**立即沉淀清洗稳定脚本**：清洗函数接收 dataframe 和需要变化的参数，返回标准明细与处置台账；
     读 raw、调用清洗、校验和写 processed 由入口串联。稳定字段与映射可用命名常量，可变阈值进参数；
   - 跑脚本产出 processed 数据并**归档**，分区规则与 raw 归档一致（优先按日期 parquet）；
   - 脚本结果与 notebook 预演**对拍一致**：字段、类型、关键明细与分组账均核对，
     金额以约定精度/容差判断，不先四舍五入掩盖差异；
   - 未确认处置不执行，也不提供删行开关绕过确认。待定项若不影响已确认版本可保留原值并标注；
     影响标准字段、金额或分析结论则先停在本步，不宣布底表可用；
   - 来源文档记录脚本、schema/规则版本、输入文件版本/指纹及对拍；场景 3.4 引用这些记录。

8. **聚合逻辑对齐**（3.3）：标准底表保持声明的明细粒度，场景聚合在第四步分析模块执行。
   多表 / 多来源聚合时，聚合口径逐项和业务对——
   按什么键 join、一对多怎么摊、单位怎么统一（元 / 万元）、两边对同一指标的理解是否一致。
   同时声明 join 基数、未匹配行、维度随时间变化的取值规则，校验 join 前后行数与金额，防止重复放大。
   对过的写进 3.3，没对过的标「待确认」。

## 规则

- 检查过的维度即使零异常也记一笔（「查过、干净」也是结论，防漏查防重查）。
- 每类异常先给行数和占比，按量排优先级——量化优先于感觉。
- 区分格式标准化与业务值处置；补值、列合并、覆盖、剔除都需记录依据与影响并经业务确认。
  原始业务值仍在 raw 保留，不能把业务处置称为「只是格式转换」。
- 剔除必须留痕：剔了多少行、多少钱，写进 3.1。
- 清洗后完整 df 没确认 → 不沉淀脚本、不写 processed；processed 是第四步起唯一取数来源，
  之后不再从 raw 预演、不重放清洗。
- 数据源级的规则、确认文档与清洗 notebook 放 `notebooks/数据清洗/`，场景内的聚合与衍生计算放场景目录。

## 完成标志

3.1~3.4 齐备：六个维度都有排查记录与业务结论、清洗预演在 notebook 可复现、
聚合口径逐项对过；清洗后完整 df 业务确认、清洗稳定脚本与 notebook 对拍一致、
processed 归档完成。之后进第四步（指标验证与稳定脚本）。
复用已有合格数据集时，以上各项引用已有来源记录；只补本场景新增依赖与对拍，不重做确认。
