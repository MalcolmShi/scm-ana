# 第零步：项目初始化

> 只补缺失的环境和目录。已有项目、新增场景不重复初始化；
> 来源接入在第二步完成，不要求尚未提供数据的新项目先读到真实 raw。

## 怎么做

1. **uv 环境与依赖**：已有项目先 `uv sync`，仅补缺失依赖。
   以下是缺环境时的示意，依赖按实际用途添加，不重复初始化：

   ```bash
   uv init            # 已有 pyproject.toml 则跳过
   uv add pandas numpy duckdb jupyter
   ```

   | 包 | 干什么 |
   | --- | --- |
   | pandas / numpy | 清洗、聚合、指标计算 |
   | duckdb | 本地数据库与 DataFrame 数据交换 |
   | jupyter | 确认 notebook 的运行环境 |

   后续步骤用到再补（如绘图库），不一次堆满。

2. **目录骨架**（已存在的跳过，不覆盖）：

   ```
   src/        # 稳定模块；职责与接口见「数据与代码约定」
   scripts/    # 按来源/场景命名的命令入口
   notebooks/  # <场景>/ 分析方案与指标确认；数据清洗/ 共享来源文档与清洗确认
   data/       # scm.duckdb：raw、processed、outputs 各自分层
   outputs/    # 可选的报告等交付物；本地服务代码在 src/ 和 scripts/
   tests/      # 离线测试（合成数据，不依赖真实归档）
   ```

   三层各归各的脚本产出（raw ← 来源导入、processed ← 第三步清洗脚本、
   outputs ← 第四步指标脚本），各步骤显式读取其输入层，不回头改上游。
   `data/` 存数据库，`outputs/` 存可选的导出交付物；本地看板按用户要求查询数据库。

3. **取数模块**：读 [数据与代码约定](数据与代码约定.md)，核对公共归档读写。
   来源明确后再建立 `read_raw_<来源>()`、`read_processed_<数据集>()`，分别供第三、四步使用。
   缺接口就补实现，不用自动换层入口顶替；日期解析和分区拼接不绑定具体来源。

4. **冒烟验证**：依赖与已实现模块可导入，已有相关测试通过；
   尚无来源时用临时 DuckDB 验证基础读写，真实来源归档和读回留到第二步验收。

   ```bash
   uv run python -c "import pandas, numpy, duckdb; print('deps ok')"
   uv run python -m unittest discover -s tests -t tests
   ```

## 规则

- 环境一律走 uv（`uv run` / `uv add`），不用裸 pip；锁文件（uv.lock）进版本库。
- 三层各归各的产出脚本：raw 由来源导入脚本按幂等与留版约定归档、processed 由第三步清洗脚本产出、
  outputs 由第四步指标脚本产出；任何层都不手改。
- 依赖进 pyproject，不装全局；notebook 里 import 的包必须已在 pyproject 里。
- 已有 `pyproject.toml`、锁文件与 `.python-version` 时优先 `uv sync`，复用现有环境；
  不在 notebook 修改 `sys.path`。

## 完成标志

环境与目录可用，相关模块可导入，基础读写验证或已有相关测试通过。
已有项目只记录补齐项，然后继续当前业务步骤。
