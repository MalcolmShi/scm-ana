# 01 · 业务意图与数据可行性（规范）

> **本文档是第 1 步的验收规范。** 按 `templates/意图确认书.md` 填写，按本文档逐项核对，业务方签署后进第 2 步（口径定义）。

六个部分：想要什么结果 → 已知什么 → 追问 → 需要哪些数据 → 有没有 → 没有怎么代。

每部分都给三样东西：**填写要求**（填什么）、**合格判据**（什么算填对）、**确认方式**（谁看、怎么看）。

---

## 一、业务意图

### 1.1 想要什么结果

**填写要求**：一句话，说明想回答什么问题、想得到什么结论。

**合格判据**：

- [ ] 不是以「分析」「统计」「看一下」开头的任务描述
- [ ] 含明确的对象和时间范围（谁的、哪段时间）
- [ ] 能回答「拿到结果怎么判断这次做对了还是做偏了」

| | 例子 | 判定 |
| --- | --- | --- |
| 反例 | 「统计降本金额」 | 任务描述，做完了也没法判断对错 |
| 正例 | 「知道今年降了多少，判断年初定的目标完成得怎么样」 | 有范围、有用途、有对错判据 |

**确认方式**：业务方口头复述一遍，说的是同一件事才算过。

### 1.2 意图要能落成档位

结果往往要分档才有用。**分几档，就要有几种动作；没有动作的档位不要设。**

**合格判据**：每档都写了「拿到之后做什么」，没有「就放着看看」这种。

例（采购增量分析的四档）：

| 档 | 拿到之后做什么 |
| --- | --- |
| 优先谈判 | 本月就谈 |
| 观察 | 按月跟踪，暂不动作 |
| 不建议 | **看过并排除**，不是去谈 |
| 新引入 | 单列待观察，没有基线不参与增长排名 |

「不建议」这一档容易被误解成「要去处理」。它存在的意义是让使用者知道
「这条看过、排除了」，避免重复翻同一批记录。

### 1.3 已知盘点

**填写要求**：两个是或否，以及各自的**具体出处**。

| 项 | 有 / 无 | 出处（必须具体） |
| --- | --- | --- |
| 已知分析逻辑 | | 文档名+章节 / 代码文件+函数 / 谁口述的 |
| 已知数据结果 | | 哪份报表 / 哪一期手工数 / 哪次汇报材料 |

**合格判据**：

- [ ] 勾「有」的，出处必须能指到具体位置，不能只写「以前算过」
- [ ] 勾「有结果」的，写清是哪一期、什么口径
- [ ] 若属「无逻辑有结果」，已写明反推得到的逻辑，以及**换另一段时间验证的计划**

四象限与处理方式：

| 已知逻辑 | 已知结果 | 这次做什么 | 工作量 |
| --- | --- | --- | --- |
| 有 | 有 | **复现 + 对账**：按老逻辑重算，与现有结果逐项比 | 最小 |
| 有 | 无 | 按现有逻辑实现，只补数据 | 小 |
| 无 | 有 | **从结果反推逻辑**，再用反推逻辑重算验证 | 中，有陷阱 |
| 无 | 无 | 完整设计 | 最大 |

第三格要特别小心。有结果没逻辑，说明有人算过但没写下来——那个结果既是校验基准，
也是反推口径的线索。但**反推出来的逻辑可能只是「能凑出这个数」的其中一种**，
实际算法不同、碰巧结果接近。

所以第三格的规矩是：**必须换另一段时间的数据再验一次**。只对得上一期，说明不了问题。

> 这一格还有白捡的好处：手算过的历史数就是现成的校验基准，第 5 步的验证不用凭空造。

**确认方式**：把出处拿给业务方，问「是这个吗」，不能自己认定。

### 1.4 追问

**填写要求**：四项必答，每项后面写清**它约束了哪个口径**。

| 问什么 | 答案 | 约束了哪个口径 |
| --- | --- | --- |
| 谁用、用来做什么决定 | | 精度、归因粒度、跨期处理 |
| 怎么算对、怎么算错 | | 能不能简化、要不要对账 |
| 多久要一次 | | 手工 / 脚本 / 定时任务 |
| 谁有权说「这个数不对」 | | 争议时谁来拍板 |

**合格判据**：

- [ ] 四项都有答案，没有「待定」
- [ ] 每项都写了约束了哪个口径——**问了但口径没变，说明这个问题问空了**
- [ ] 「谁有权说不对」有具体的人或岗位，不是「业务方」

**确认方式**：业务方逐项确认，尤其第三项（频率）——它常被忽略，但直接决定实现方式。

## 二、数据需求与可行性

### 2.1 需要哪些数据

**填写要求**：按业务对象列，不按表列。

| 维度 | 数据项 | 用途（支撑哪个口径） | 粒度 | 必需/可选 |
| --- | --- | --- | --- | --- |
| 主体 | | | | |
| 对象 | | | | |
| 行为 | | | | |
| 金额 / 数量 | | | | |
| 时间 | | | | |

五个维度的含义：

| 维度 | 问什么 | 例 |
| --- | --- | --- |
| 主体 | 谁的 | 公司、部门、门店 |
| 对象 | 什么东西 | 商品、客户、产品、项目 |
| 行为 | 发生了什么 | 下单、退货、替换、生效 |
| 金额 / 数量 | 多少 | 单价、数量、金额、税率 |
| 时间 | 什么时候 | 生效日、发生日、核算周期 |

**合格判据**：

- [ ] 每项都写了用途，且用途能对应到 1.1 的意图
- [ ] 每项都标了粒度（行级 / 单据级 / 日级 / 月级）
- [ ] 每项都标了必需或可选——**必需的不能留空**
- [ ] 没有把表名当数据项（「订单明细表」不是数据项，「下单单价」才是）

这是需求清单，不是数据库设计。表怎么建是后面的事。

### 2.2 可得性核查

**填写要求**：逐项核查，**必须问业务，不能自己看表结构判断**。字段存在不等于数据可用。

| 数据项 | 档位 | 依据 | 后续动作 |
| --- | --- | --- | --- |
| | 有且可用 / 有但存疑 / 没有 | 业务确认 + 抽样结果 | |

三档的判断标准：

| 档 | 判断依据 | 后续动作 |
| --- | --- | --- |
| 有且可用 | 业务确认 + 自己抽样看过 | 直接进数据模型 |
| 有但存疑 | 有字段，但录入率、口径、覆盖率不确定 | 进 2.3，按替代方案处理 |
| 没有 | 业务明确说没有 | 进 2.3，找替代或缩范围 |

**合格判据**：

- [ ] 每一项都有档位，没有空着的
- [ ] 勾「有且可用」的，附了抽样证据：非空率、抽样行数、覆盖的时间范围
- [ ] 勾「有但存疑」的，写明了存疑的具体表现（如「非空率 30%」「两系统填法不同」）
- [ ] 勾「没有」的，写明是问谁确认的、什么时候问的
- [ ] 没有一项是凭「表里有这个字段」判定的

**「有但存疑」最常见，也最容易被放过。** 字段在那儿，但实际不可用——这种事只有抽样看过才知道。

**确认方式**：业务方逐项过，尤其「有但存疑」的项——它决定后面要不要做替代。

> 这一步必须在第 1 步做，不能留到取数时。否则方案设计两周，最后发现关键数据没有，两周全废。

### 2.3 替代方案

**填写要求**：只填「存疑」和「没有」的项。每个替代必须写三段。

| 不可得的数据 | 替代用什么 | 能回答什么 | **不能回答什么** |
| --- | --- | --- | --- |
| | | | |

**合格判据**：

- [ ] 每个不可得项都有结论：要么有替代，要么明确写「无替代，缩小范围」
- [ ] 每个替代都写了**「不能回答什么」**——第三段不写，这个替代就是隐患
- [ ] 替代的有效性对得上 1.1 的意图粒度（见下表）

判据不是「像不像」，而是：**用替代数据算出的结论，与用理想数据算出的结论，在决策层面是否一致。**
关键在于「决策层面」，它由 1.1 的意图粒度决定：

| 想要的结果 | 理想数据 | 替代方案 | 有效吗 |
| --- | --- | --- | --- |
| 看整体趋势 | 实际谈判降价额 | 单价变化 × 数量 | **可用**——市场自然降价也计入，但趋势方向仍成立 |
| 考核谈价能力 | 实际谈判降价额 | 单价变化 × 数量 | **不可用**——分不清是谈下来的还是市场降的 |

替代不成立时，还有三条退路：缩小分析范围、改用另一个能成立的结论、明确标注局限后交付。

**确认方式**：业务方明确表态「这个替代能不能接受」，不能默认接受。

## 三、核对与签署

### 3.1 填表人自查

逐节过一遍上面的合格判据，全文没有「待定」「大概」「后续确认」这类字样。

### 3.2 业务确认签署

| 确认项 | 确认人 | 日期 | 结论 | 备注 |
| --- | --- | --- | --- | --- |
| 意图是否准确 | | | 通过 / 有异议 | |
| 已知出处的信息 | | | 通过 / 有异议 | |
| 数据可得性判断 | | | 通过 / 有异议 | |
| 替代方案可接受 | | | 通过 / 有异议 | |

**四项全部通过才算第 1 步完成。** 有异议的进 3.3，不能带着异议往下走。

**Agent 对话场景的降级**：业务方即当前对话用户时，用户在对话中逐项确认（或对四项一次性确认）即可视为签署——把确认内容与时间记入上表，注明「对话确认」。**拿不到确认就不进第 2 步；用户没回复不是默许。**

### 3.3 遗留问题

只放真正需要业务拍板的：影响口径、且没有唯一合理解释的。

| 问题 | 影响哪个口径 | 需要谁确认 | 何时确认 | 状态 |
| --- | --- | --- | --- | --- |
| | | | | 挂起 / 已解决 |

**挂起项不阻断其他已确认的部分**，但涉及金额或核心口径的挂起项，必须在第 2 步开始前清掉。

## 四、变更记录

口径一旦确认，改动必须留痕。没有变更记录，三个月后没人记得为什么改。

| 日期 | 变更内容 | 原因 | 影响范围 | 确认人 |
| --- | --- | --- | --- | --- |
| | | | | |

**规则**：改 1.1 的意图、2.2 的可得性判断、或 2.3 的替代方案，都必须重新走一遍 3.2 的签署。
改了却不重签，等于没有确认。

---

## 五、门禁

进第 2 步之前必须全过。

**意图**

- [ ] 能说出「这次做对了 / 做偏了」的判据
- [ ] 每档输出都有明确的使用动作
- [ ] 已知盘点落在四象限的哪一格，且出处具体
- [ ] 属「无逻辑有结果」的，反推逻辑已安排换期验证
- [ ] 追问四项都有答案，且都约束了口径

**数据**

- [ ] 数据需求按五个维度列全，每项有用途、粒度、必需/可选
- [ ] 每项可得性都跟业务确认过，不是自己看表名猜的
- [ ] 「有但存疑」的项已抽样核实并写明具体表现
- [ ] 不可得项都有结论，替代方案写了「不能回答什么」

**签署**

- [ ] 3.2 四项全部通过
- [ ] 涉及金额或核心口径的挂起项已清掉
