# 03 · 取数与清洗

链路第 3–4 步。取数一句话，清洗是重头。

## 一、取数与多源关联

取数不只是「把数据读进来」，包含三件事：定窗口、齐字段、**把多个源对齐**。
只有一个源时第三件自动成立；一旦接入第二个源，它就是最容易出错的一步。

### 取数前先确认四个约定

| 项 | 要确认什么 |
| --- | --- |
| 读取层 | 读哪一层？——**优先 `processed`（清洗后底表），无底表才读 `raw`** |
| 归档结构 | 数据按什么路径组织？ |
| 入口 | 用哪个取数函数？参数怎么决定范围与粒度？ |
| 时间窗口 | 目录/分区日期与业务日期的关系？ |

这四项的**正本在来源模块代码与项目的来源接入文档**，不在本 skill——以那里为准，不要凭印象猜。
**「优先读清洗层、不读原始层」这条对任何来源都不变。**

### 字段从口径来，不从表来

源表往往几十列，能算的指标很多，但**能算不等于该算**。

先定口径（第 2 步），再回头看需要哪几列。先翻表再想指标，结果是一堆
「因为字段存在所以算了」的装饰性指标——它们会挤进报表，让真正的信号被淹没。

### 每个过滤都要留痕

任何缩小数据范围的动作，都要能回答「因为这条口径少了多少」。

例（真实）：只保留「外部单位」这一类供应商，因为关联单位之间不是市场议价关系，
排除是对的；但如果不在报告里说，报告金额就会比财务口径少一截，看报告的人不知道差在哪。

做法：排除行数、排除金额进 `meta`，写进运行摘要。
同样适用于金额准入、无效记录过滤、业务范围限定。

### 多源关联

接入第二个源的那一刻，风险从「数据脏」变成「关系错」。关系错不报错，只会算错。

#### 1. 关联键用编码，不用名称

名称会变、会重名、带空格和全角。编码才是稳定键。

| 关联键 | 可用性 |
| --- | --- |
| 业务编码（客户编码 / 商品编码 / 单据号等） | **首选** |
| 系统内唯一 ID | 可用，但只在本系统内有效 |
| 名称 | 最后手段，且必须留匹配日志 |
| 名称 + 规格 + 单位 组合 | 比名称好，但仍可能一对多 |

名称匹配必须输出匹配结果（匹配上几条、哪些没匹配上），**不能匹配完就丢掉**。

#### 2. 匹配不上的三种情况，都不许静默处理

| 情况 | 错误做法 | 正确做法 |
| --- | --- | --- |
| 一源有一源无 | 内连接直接丢掉 | 外连接，未匹配的单独输出「待核对清单」 |
| 一对多 | 取第一条 / 取金额最大那条 | **交人工确认**，程序不替业务做选择 |
| 多对多 | 直接笛卡尔积 | 关系本身有问题，退回口径重定义 |

**「匹配不上」是业务信息，不是脏数据。** 丢掉它，等于把口径问题藏起来。

#### 3. 不能靠数值关系猜匹配

**例（真实）**：「入库价低于调价后价格」看起来是降本生效的证据，但不能作为匹配依据——
不同采购主体、独立采购价格可能同时存在，同一物料在不同主体下价格不同是正常的。

**做法**：匹配只能基于**显式关系**（编码 + 适用主体 + 生效日期区间），不能基于「数值看起来对得上」。
数值关系可以用来**事后校验**匹配结果，不能用来**决定**匹配。

#### 4. join 之前先定「一行该匹配几行」

多源 join 最常见的错误是行数放大：一条记录匹配上多条，金额被重复累加，**而代码不报错**。

做法：

1. join 前写明预期基数（1:1 / 1:N / N:1）
2. join 后立刻校验行数
3. 断言写进 notebook：

```python
assert len(merged) == expected_rows, f"join 后行数 {len(merged)}，预期 {expected_rows}"
```

**如果 1:N 是业务允许的**（例如一条主单可以支持多条生效中的明细），
那就要在计算时限制每条明细只取自己的增量，而不是把结果直接求和。

#### 5. 人工填报源要多一层校验

人工填报的数据，缺的不是格式，是**逻辑一致性**。

| 校验 | 例子 |
| --- | --- |
| 数值关系 | 原价 > 现价（降价场景方向才对）、数量 > 0 |
| 时间关系 | 生效日期不早于关联单据日期、不在未来 |
| 单位关系 | 换算系数 × 原单位 = 可比单位，且能反算 |
| 完整性 | 关联的新旧对象都存在且状态有效 |
| 重复 | 同一对象同一生效日不重复填报 |

**校验不通过的要能回传给填报人**，而不是只在结果里「暂不计算」。
只在结果里消失，填报人永远不知道自己填错了。

#### 6. 同一概念多个口径并存时，先分层再关联

| 情形 | 处理 |
| --- | --- |
| 集团统一定价 + 主体独立价格 | 先按主体拆，各自关联，最后汇总 |
| 含税价 + 不含税价混用 | 关联前统一到同一口径，不能一边含税一边不含税 |
| 不同计量单位 | 关联前换算到可比单位，换算系数单独成列留痕 |
| 一个上游对象适用多个下游对象 | 显式展开成关系表，不要在计算时临时判断 |

## 二、清洗

### 六步流程

顺序不能跳。**口径没识别清就做归并，一定会返工。**

| 步 | 做什么 | 产出物 | 落在哪 |
| --- | --- | --- | --- |
| 1 字段盘点 | 每列的类型、唯一值数、非空率、一句话说明 | 字段清单表 | 来源文档「字段结构」 |
| 2 取值审计 | 枚举字段全量列取值+行数；高基数抽样；单位与量纲 | 枚举表 | 来源文档「取值审计」 |
| 3 口径识别 | 找同一业务概念在不同系统/文件/方向下的表达差异 | 口径对照表 | 来源文档「口径差异」 |
| 4 异常识别 | 按六类异常逐类过滤，统计行数与样本 | 异常清单 | notebook 清洗核查 |
| 5 处置决策 | 每个字段/每类异常给出处置与理由 | 决策表 | 来源文档「清洗规则」 |
| 6 断言校验 | 定不变量，清洗后逐条跑 | 断言清单 | 来源文档「断言校验」+ notebook |

**「口径差异」单独成节是关键**：它是最容易出错、也最容易被后续维护者忽略的部分。

### 六类异常

用统一词汇，避免「脏数据」「异常值」这类含糊说法。

| 类型 | 定义 | 典型信号 | 常见处置 |
| --- | --- | --- | --- |
| 缺失 | 该有值却没有 | 非空率低于同组字段 | 补、置空、或确认不适用 |
| 脏值 | 取值不在合法域内 | 单位列出现 `arr`、编码带空格 | 置空或映射 |
| 口径冲突 | 同一概念多种表达，或同名字段不同含义 | 两系统叫法不同、后缀差异 | 统一到一列或拆成两列 |
| 重复 | 完全重复或业务重复 | 全列重复、单据+明细+批次重复 | 去重（需业务确认） |
| 勾稽失衡 | 字段间算术关系不成立 | 数量×单价≠金额、明细≠汇总 | **修正口径而非改数** |
| 语义混装 | 一个字段承载两种含义 | 分类字段里混着两类不同性质的值 | 拆列 |

**判定的第一步永远是分组看。** 同一个字段在不同来源系统、不同方向、不同时间上
可能有完全不同的表现，先做交叉表再下结论。

## 三、五条判定原则

踩过的坑收敛出来的，遇到新问题时先对照。下面每条的例子都来自真实项目。

### 1. 分母原则：覆盖率必须用「适用行」做分母

**例**：某个单价字段全表只有 0.2% 有值，判为「实质空列，建议丢弃」。
实际上它只对退货行有意义——退货行里覆盖 56.7%。用全量当分母，等于把 99.6% 的
正常行算成了缺失。

**做法**：先问「这个字段对哪些行适用」，再用适用行数做分母。

### 2. 符号原则：`0` 不等于「不适用」，正负号可能承载业务

**例一**：退货行的单价字段为 0，其实是「不适用」，留 0 会让平均单价的分母虚增。
**例二**：`进价 > 售价` 直接比较得出 155 行「倒挂」，全是负数符号造成的假象，
按绝对值比是 0 行。

**做法**：区分「值为 0」与「不适用」（用 null）；比较金额先想清楚带不带符号。

### 3. 依赖原则：先查函数依赖，能删维度就不造维度

**例**：某个类型字段的「合同」后缀完全由「来源系统」决定（A 系统无、B 系统有）。
如果拆出「是否签合同」这个维度，它等价于系统，是假信息。

**做法**：归并前先做交叉表，看目标取值是否被另一个字段唯一决定；是的话直接删后缀，
不新增维度。

### 4. 守恒原则：清洗前后要能对上账

**例**：去重 209 行会改变金额合计 57.05 万（0.37%）。这种「顺手去重」必须显式记录，
否则报表数字变了没人知道。

**做法**：行数、金额、数量在清洗前后各记一次；任何不等都要能解释。

### 5. 断言原则：清洗必须留下可复跑的不变量

**例**：`单价 × 数量 = 金额` 在修正口径前只有 7 行成立，修正后全表 4 万余行逐行成立。
这条恒等式比任何肉眼核对都可靠。

**做法**：每个源至少定 2 条断言（一条勾稽、一条守恒），写进 notebook 和文档，每次清洗后跑。

## 四、五种处置 + 一种挂起

| 处置 | 含义 | 判据 |
| --- | --- | --- |
| 保留 | 原样进底表 | 取值合法、语义清晰 |
| 规范化 | 改类型或格式，值域不变 | 类型不对（str→datetime）、编码当数字、全角残留 |
| 归并 | 合并取值，减少基数 | 同义不同名；有函数依赖；脏值可映射 |
| 标记 | 值不动，加布尔列 | 异常值是真实业务（赠品、红冲、临期），删了就丢信息 |
| 丢弃 | 不进底表 | 全常量、可由他列派生、一一对应冗余、自由文本无对照、业务明确不用 |
| 挂起 | 需业务确认 | 影响金额或口径，且没有唯一合理解释 |

**丢弃的五条判据要逐条对照，不要凭感觉。** 只要有一条站不住，就改成「标记」。

## 五、交付规范

### 底表（processed）

- 路径与 raw 同构，元数据沿用来源与时点两列
- 归并字段：**保留原值列，派生列追加在后面**，不覆盖原始取值
- 幂等：同一份 raw 重跑必须得到逐字节相同的 processed

### 来源文档（固定八节）

见 `templates/来源文档.md`：来源与接入 → 字段结构 → 取值审计 → 口径差异 →
清洗规则 → 断言校验 → 执行 → 待确认。

- [ ] 每个丢弃字段是否对得上五条判据之一

- [ ] 清洗前后行数 / 金额是否守恒或差异可解释
- [ ] 挂起项是否写清「需要谁确认什么」
