# 04 · notebook 验证

链路第 5 步。

notebook 的价值只有一个：**中间态可检查、可讨论、可回退。**
批处理管线从输入直接到成品，口径错了要到看到报告才发现；notebook 让人在算到一半时
就能说「等一下，这个数不对」。

## 一、首格固定五问

```markdown
## 本 notebook 回答什么问题
## 口径（引用方案文档哪几节、哪组阈值常量）
## 输入（取数门面函数的取数范围、数据覆盖）
## 验证点（3-5 条，逐条打勾）
## 结论（稳定后提取到哪个分析模块）
```

五问写不全就先别开算——说明想清楚的程度还不够。

模板见 `templates/notebook契约.md`。

## 二、验证点必须先写后算

验证点是「**我预期看到什么**」。先写下来，才能发现「实际不是这样」。
算完再补验证点，等于用结果反推预期，验证就失效了——那不是验证，是追认。

反例：跑出结果后发现「最高档有 3 条」，于是写下验证点「最高档应该有 3 条」。
这条验证点永远通过，也永远没有价值。

## 三、三类验证点，每类至少一条

| 类 | 查什么 | 例子 |
| --- | --- | --- |
| 守恒 | 分组汇总能不能对上总计 | 各档记录数之和 = 报告总行数 |
| 边界 | 阈值两侧的行为对不对 | 指标恰好等于阈值的那条记录归入高优先档 |
| 反例 | 已知的坑有没有复发 | 无基线记录的值是 `NaN`，不排进前三位 |

三类分别对应三种失败模式：算漏了、判错了、老毛病又犯了。

### 与断言的关系（两套词汇，别混）

| | 断言（四类：勾稽/守恒/值域/唯一性） | 验证点（三类：守恒/边界/反例） |
| --- | --- | --- |
| 验收对象 | **清洗层**（第 4 步的底表） | **分析层**（第 5 步的计算结果） |
| 定义位置 | 来源文档第六节 + `templates/断言清单.md` | notebook 首格 + 实施方案第四节 |
| 「守恒」含义 | 清洗前后金额/行数对得上 | 分组汇总对得上总计 |

清洗断言全过，才有资格开始写分析验证点；两者不是同一件事的重复检查。

## 四、写法对照

| 坏 | 好 | 为什么坏 |
| --- | --- | --- |
| 检查数据是否正常 | 每个实体都有 12 行周期记录，无缺周期 | 「正常」没有判定标准，无法打勾 |
| 看一下结果合不合理 | 各档记录数之和 = 报告总行数 | 「合理」是主观的，验证不了 |
| 确认没有异常值 | 无 `inf` / `NaN` 混入最高档前三位 | 「异常值」不知道指哪个，也没说怎么算 |
| 核对排名对不对 | 最高档内按指标降序，`NaN` 排档内最后 | 没说按什么排序、空值排哪 |

**判断标准只有一条：一条验证点如果没法写成 `assert`，就是没写好。**

## 五、验证点最终落在哪

| 类型 | 去向 | 什么时候 |
| --- | --- | --- |
| 守恒、边界 | 自动化断言（项目的测试目录） | 提取到分析层代码后 |
| 反例 | 留在 notebook，可复跑 | 永久保留 |
| 一次性核对 | 只留在 notebook 输出里 | 不转成断言 |

提取后 notebook **不要删**。它是下次复核的入口，也是新人理解口径的最快路径。
